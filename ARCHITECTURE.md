# Единый стек и архитектура: ЛК, магазин, «Друг клуба»

Статус: предложение, ждёт решения владельца. Составлено по фактам из двух проектов, ничего в `coral-club-shop` не менялось.

## 1. Что есть сейчас

| | `coral-club-shop` («Друг клуба», лендинги) | `coral-club-lk-test` (ЛК) |
|---|---|---|
| Фронтенд | Next.js 16.3 (static export), React 19, TypeScript, CSS Modules | чистый JS без сборки, один `style.css` + `friend.css` |
| UI | токены `styles/tokens.css`, kit `src/components/ui` (Accordion, Button, Chips, Container, Rating, Section, Sheet, Stack, Text), страница `/_ui-kit` | свои классы, часть стилей перенесена скриптом из CSS-модулей |
| Чек-аут | `FriendCheckout.tsx` (1756 строк), `shopApi.ts`, `addressSearch.ts`, `PickupSheet`, `OptionCards`, `FloatInput`, `shopPay.ts` | `checkout.js`, вручную повторяет то же самое |
| Посредник к магазину | `scripts/dev-proxy.mjs` (локально, :3200) | `server.mjs` (локально, :3300) и `worker/` (Cloudflare) |
| Хостинг | GitHub Pages `/coralclub/`, отдельная сборка на coralclub.ru | GitHub Pages `/coralclub-lk/docs/` |

Проблемы: два стека; одна и та же логика чек-аута написана дважды; **три посредника** к одному и тому же магазину; компоненты «Друга клуба» тянут стили друг у друга (`friend/*` импортирует `landing/LandingCheckout.module.css`), то есть общего слоя фактически нет; тестов нет.

## 2. Решение по стеку

**Один стек: Next.js (static export) + React + TypeScript + CSS Modules + `tokens.css` + общий UI kit.** Он уже стоит в `coral-club-shop` и уже размещает несколько продуктов в одном приложении (`/friend`, `/landing`, `/lab`, `/account`, `/_ui-kit`).

Рекомендация: **ЛК становится ещё одним разделом того же приложения** (`src/app/lk/…`), а не отдельным проектом.
- ничего не нужно «портировать»: чек-аут, адресный поиск, пункты выдачи, карточки выбора, слоты курьера, токены и kit уже там;
- один деплой на GitHub Pages и один набор правил (`AGENTS.md`, линтер, типы);
- прежний репозиторий ЛК остаётся прототипом и источником проверенной логики (сессия по токену, прокси, Worker), потом архивируется.

Альтернативы (отклонены): монорепо с пакетами (`apps/*`, `packages/ui`, `packages/gateway`) — правильно при 3+ приложениях и нескольких командах, сейчас это переезд существующего проекта ради структуры; два репозитория с опубликованным UI-пакетом — лишние версии и релизы для одного разработчика.

## 3. Единый UI kit

Сейчас в kit нет того, на чём стоит чек-аут. План выноса (в `src/components/ui` и `src/components/checkout`):
1. `FloatInput`, `OptionCard(s)`, `OptionInfo`, `Check`/`Consent`, `Loader`, `FormSection` — из `friend/` и `landing/` в `ui/`, с одним CSS-модулем на компонент и только токенами (без импортов стилей из соседних разделов).
2. `AddressSearch`, `PickupSheet`, `CourierSlots`, `CountryMenu` — в `components/checkout/`, без привязки к «Другу клуба».
3. Витрина всех компонентов на `/_ui-kit` (уже есть) как единственное место, где их смотрят и принимают.
4. Правило: раздел приложения не импортирует стили другого раздела, только `ui/` и `checkout/`.

## 4. Общее ядро чек-аута

`FriendCheckout` (1756 строк) смешивает данные, правила и разметку. Разделить:
- **хуки без разметки**: `useShopSession`, `useDelivery`, `usePayments`, `useTotals`, `useAddress`, `usePickup`, `useSlots`, `usePromoBonus` (`src/lib/checkout/`);
- **интерфейс `ShopGateway`** (`get(path, params)`, `createOrder(body)`, `session()`): реализации «гость/друг клуба» (прокси, куки) и «участник» (токен API → посредник);
- **`Market`** (RU, DE, US): валюта, способы получения, флаги вроде `cardForm`, `pickup`, `deliveryNeedsRegion` (сейчас `lib/market.ts` описывает один рынок);
- экраны `FriendCheckout` и `LkCheckout` становятся тонкими и различаются только шлюзом, рынком и текстами.

## 5. Микросервисы: нужны ли

Короткий ответ: **нет, модульный монолит плюс один граничный сервис.** Причины: один разработчик, два деплоймента, нагрузка небольшая; микросервисы добавили бы версионирование контрактов, сетевые задержки и эксплуатацию без выигрыша.

Границы (контексты) выделяем **в коде**, а не в сети:

| Контекст | Где живёт | Источник данных |
|---|---|---|
| Идентификация | `lib/cc4/auth` | API кабинета (`auth/session`, `auth/login`) |
| Каталог, избранное | `lib/cc4/catalog` | API кабинета, браузер ходит напрямую (CORS открыт) |
| Корзина | `lib/cc4/basket` | API кабинета, напрямую |
| Чек-аут | `lib/checkout` | магазин `/sv-api/*`, только через шлюз |
| Оплата | `lib/checkout/pay` | передача на страницу банка |
| Адрес | `components/checkout/AddressSearch` | Google Places (ключ у шлюза) |
| Кабинет | `lib/cc4/account` | API кабинета |

**Единственный отдельный сервис — `checkout-gateway`** (сейчас `worker/`): брокер сессии магазина и прокси по списку разрешённых путей. Это настоящая граница, потому что магазин не пускает браузер с другого домена (см. `README`, проверено: сессию нельзя ни получить, ни передать заголовком). Его надо свести к **одному коду на две среды**: ядро на стандартном `fetch` (`bootstrap` и обработчик уже так написаны) + адаптеры Cloudflare Worker и Node для разработки. Тогда `server.mjs` и `scripts/dev-proxy.mjs` уходят: вместо трёх посредников один.

Когда пересмотреть и выделять сервисы: появится вторая команда или SLA на чек-аут; нужен собственный бэкенд (заказы, лиды) вне магазина; шлюз упрётся в лимиты Cloudflare. Первым кандидатом будет отдельный сервис заказов и лидов.

## 7. Риски

- Репозиторий `coral-club-shop` публикует ещё и лендинг на coralclub.ru (labspace): `/lk` не должен попадать в ту сборку (`pageExtensions`).
- Адреса меняются: ЛК будет по `/coralclub/lk/` вместо `/coralclub-lk/docs/`; `ALLOWED_ORIGINS` у Worker остаётся тем же (тот же домен `github.io`).
- Рефакторинг `FriendCheckout` затрагивает работающий проект: этап 3 делаем маленькими шагами, каждый со сверкой на странице «Друга клуба».
- Лицензионные шрифты и ключи не добавляются в репозиторий (как сейчас).
