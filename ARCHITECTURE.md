# Coral Club: единый продукт (магазин + личный кабинет), API first

Версия 2. Заменяет первое предложение («ЛК как раздел магазина»): теперь цель шире, один продукт из независимых сервисов с общим Layout. Решения этой версии ждут подтверждения владельца (раздел 8).

## 1. Принципы

1. **API first.** Источник правды — бэкенд Coral Club: API кабинета `api.coral.club` (OpenAPI на `/docs`) и чек-аут магазина `/sv-api/*` за нашим шлюзом. Фронтенды не знают ни про Bitrix, ни про куки магазина.
2. **Один продукт, несколько независимых сервисов.** Магазин, личный кабинет, оформление и общая оболочка (Layout) собираются и выкладываются отдельно.
3. **Один Layout.** Шапка, меню и корзина — отдельный сервис, который подключают все остальные. Свои шапки в сервисах запрещены.
4. **Один UI kit и один набор токенов.** Сервисы не импортируют стили друг друга.
5. **Сначала то, что приносит заказ.** Порядок работ: шлюз оплаты на GitHub → микросервисная архитектура → идеальный интерфейс.

## 2. Что значит «микросервисы» здесь

Два слоя, и путать их нельзя.

**Фронтенд-сервисы (микрофронтенды)**, каждый со своей сборкой и своим путём на одном домене:

| Сервис | Путь | Что внутри |
|---|---|---|
| `layout` | `/layout/layout.js` | шапка, меню, корзина (бейдж и выдвижная корзина), выбор страны, вход |
| `shop` | `/` | каталог, карточки товаров, лендинги, «Друг клуба» |
| `checkout` | `/checkout/` | оформление и оплата, общее для магазина и кабинета |
| `lk` | `/lk/` | профиль, баланс, структура, заказы, задачи, показатели |

**Серверные сервисы:**
- бэкенд Coral Club (API кабинета, магазин): уже есть, он чужой для нас, мы его только вызываем;
- **`gateway`** (Cloudflare Worker, наш единственный серверный сервис): держит сессию магазина вместо браузера, пропускает только нужные пути, отдаёт адрес банка, ключи Google. Больше своих серверных сервисов не заводим, пока нет причины (раздел 7).

Почему так: статический хостинг (GitHub Pages) и один разработчик. Сетевые границы дороги, поэтому они проходят только там, где их навязывает среда: между браузером и магазином (шлюз) и между независимо выкладываемыми фронтендами.

## 3. Layout как сервис

Layout должен подключаться из любого сервиса на статике, без серверной сборки страниц. Предлагается **веб-компонент плюс композиция по путям**:

- `layout` публикует один файл `layout.js` с кастомным элементом `<cc-layout active="shop">`;
- каждый сервис остаётся своей статической сборкой, подключает `layout.js` и вставляет `<cc-layout>` вверху страницы; Layout рисует шапку, меню и корзину;
- переходы между сервисами обычные ссылки (полная загрузка, кэш браузера), поэтому не нужна рантайм-федерация модулей;
- общее состояние живёт в одном origin: `localStorage`/`sessionStorage` (токен, страна, корзина) и `BroadcastChannel("cc")` для событий между вкладками.

**Контракт Layout** (версионируется, ломающие изменения только с новой версией):

| Что | Вид |
|---|---|
| атрибуты | `active` (shop, lk, checkout), `country`, `locale` |
| события наружу | `cc:cart:changed`, `cc:auth:changed`, `cc:country:changed` |
| вызовы внутрь | `window.coralLayout.cart.add(code, qty)`, `.open()`, `.count()` |
| слоты | `actions` (кнопки в шапке, например «Войти») |
| стили | токены `--cc-*` из UI kit, внешние стили Layout не меняют |

**Корзина в общем меню.** Корзина принадлежит Layout, а не магазину: данные из `/basket/*` API, выдвижная корзина (тот же `CartDrawer`, который уже работает), бейдж с количеством в шапке на всех страницах. Магазин и кабинет только вызывают `cart.add(...)`.

Отвергнуто: Module Federation и single-spa (тяжело для статики и для одного разработчика), iframe (ломает сессию и адреса, плохо с оплатой).

## 4. API first на практике

- **Контракт.** OpenAPI API кабинета (`/docs`, около 1,5 МБ) → типы и клиент генерируются в пакет `@coral/api`. Ответы без схем (чек-аут магазина `/sv-api/*`, `/init`, `/delivery`, `/payments`, `/order`) описываем руками: схемы и типы в `@coral/api/shop`, проверка ответа на границе.
- **Шлюз.** Единственный путь к чек-ауту магазина. Список разрешённых путей и методов лежит в одном месте и проверяется тестами; POST только на `/sv-api/order`.
- **Мок по контракту.** Для разработки и тестов без реальных заказов: мок API кабинета и шлюза (уже есть рабочий образец, на нём проверены корзина и оформление).
- **Версионирование.** Layout, шлюз и клиент имеют версию контракта; сервисы указывают, с какой версией работают.
- **Известные пробелы контракта** (проверено на живых ответах): страница оплаты магазина отвечает редиректом, ссылка оплаты заказа в API (`paymentLink`) ведёт на страницу заказа в кабинете, в схемах API нет ответов чек-аута. Всё это закрывается шлюзом.

## 5. Репозитории и пакеты

Целевая структура: **монорепозиторий с workspaces** (сегодня код лежит в `coral-club-shop` одним Next-приложением и в `coral-club-lk-test` на чистом JS).

```
apps/shop        # магазин и «Друг клуба»
apps/lk          # личный кабинет
apps/checkout    # оформление и оплата
packages/layout  # веб-компонент <cc-layout>
packages/ui      # токены и UI kit (FloatInput, OptionCards, CartDrawer, ...)
packages/api     # клиент по OpenAPI и схемы чек-аута
packages/gateway # ядро шлюза + адаптеры Cloudflare Worker и Node (для разработки)
```

Границы проверяются линтером: приложение импортирует только `packages/*`, приложения друг друга не импортируют.

## 6. Путь миграции (без остановки продукта)

0. **Сделано.** Общий UI kit и слой `checkout`, сменный транспорт магазина, клиент шлюза, шлюз на Worker, корзина и оформление кабинета на общих компонентах (`/lk/cart`, `/lk/checkout`), русские подписи.
1. **Шлюз оплаты на GitHub.** Оформление в ЛК доходит до шлюза оплаты по стране. Статус и что осталось проверить на живом онлайн-заказе: раздел 9.
2. **Границы в коде.** Разложить `coral-club-shop` по `apps/*` и `packages/*` в одном репозитории, без изменения внешнего поведения; включить правило запрета импортов между приложениями.
3. **Layout.** Вынести шапку, меню и корзину в `packages/layout` (веб-компонент), подключить в `shop` и `lk`, убрать собственные шапки.
4. **Раздельные деплои.** Каждое приложение выкладывается своим процессом под своим путём; общий домен и общий origin сохраняются.
5. **Один шлюз.** Свести `server.mjs`, `dev-proxy.mjs` и Worker к одному коду на две среды, удалить лишние.
6. **Тесты и CI.** Юнит-тесты правил (слоты, разбор адреса, итоги, список путей шлюза), контрактные тесты по OpenAPI, сборка и линт на каждом коммите.
7. **Идеальный интерфейс.** Дизайн-проход по готовому набору компонентов (после того как сервисы и Layout стабильны).

## 7. Когда выделять ещё серверные сервисы

Сейчас не нужны. Пересмотреть, если: появится вторая команда; потребуется собственный бэкенд вне Coral Club (заказы, лиды, аналитика, личные данные); шлюз упрётся в лимиты Cloudflare; нужен SLA на оформление. Первыми кандидатами будут сервис заказов и лидов и сервис адресов (прокси Google с кэшем).

## 8. Что нужно решить владельцу

1. **Монорепозиторий с workspaces** как цель (раздел 5): да или нет.
2. **Механизм Layout** (раздел 3): веб-компонент и композиция по путям (рекомендация) или другой.
3. **Где жить новым пакетам:** внутри `coral-club-shop` (рекомендация, меньше переездов) или в новом репозитории.

## 9. Состояние шлюза оплаты (приоритет 1)

Проверено на реальных данных:
- сессия магазина открывается по токену API кабинета без пароля (ссылка `web_views` и заголовок `x-access-token`);
- корзина API и корзина магазина одна и та же;
- ссылка оплаты заказа (`paymentLink`) принимает относительный `url`: страница оплаты открывается с сессией участника;
- для заказов с оплатой курьером шлюза нет (магазин возвращает в список заказов), поэтому в кабинете оставлена только онлайн-оплата;
- Pages-деплой ЛК упал один раз по тайм-ауту на стороне GitHub (ошибка «Timeout reached»), пересобран.

- **переход на банк найден** (проверено на заказе с картой, РФ): короткий адрес оплаты ведёт на страницу «Проверьте и оплатите ваш заказ»; блок банка на ней пуст, пока не выбран способ. Страница сама шлёт `POST /ajax/order/orderSelectPaysystem.php` (`sessid`, `order_id`, `delivery`, `paysystem` вида `156:bank_card`) и вставляет ответ (`paysystems_action`) с кнопкой банка. Шлюз повторяет этот шаг со способом, выбранным в чек-ауте, и отдаёт адрес банка (для карты ЮKassa, `yoomoney.ru/checkout/...`);
- перед переходом на оплату чек-аут магазина ставит cookie `orderResultId=<номер>`, шлюз делает так же;
- окна подтверждения нет: «Перейти к оплате» создаёт заказ и сразу открывает банк. Если банк не найден, остаётся экран заказа с повтором (сайт магазина в браузере без сессии привёл бы на страницу входа).

## 10. Риски

- Композиция по путям на GitHub Pages требует одного origin: при выносе сервисов на другие домены сломается общее состояние (токен, корзина).
- Рефакторинг `FriendCheckout` (около 1700 строк) затрагивает работающий проект: делать малыми шагами со сверкой на странице.
- Ключ Google Places попадает на страницу при сборке: в сборке GitHub Pages его сейчас нет, поиск адреса там работает только если ключ передать в сборку или отдавать со шлюза во время работы.
- Лицензионные шрифты и ключи не добавляются в репозиторий.
